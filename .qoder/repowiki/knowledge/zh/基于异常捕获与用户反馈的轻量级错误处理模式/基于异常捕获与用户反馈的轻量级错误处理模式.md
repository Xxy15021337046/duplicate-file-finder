## 1. 系统/方法概述

该仓库没有定义统一的自定义异常类型体系或全局错误码，也没有使用日志框架（如 `logging`）。整体采用**“局部 try/except + 用户界面反馈”**的轻量级错误处理模式：
- 核心引擎层（`core/`）对 I/O、数据库、第三方库调用进行细粒度 `try/except Exception` 捕获，记录到本地 `_log` 并通过回调上报。
- GUI 层（`gui_modules/`）在后台线程中执行扫描任务，用顶层 `try/except` 捕获所有异常，通过 `tkinter.messagebox.showerror` 弹窗向用户报告，并保证 UI 状态恢复。
- 通过 `threading.Event` 作为停止标志，配合 `raise InterruptedError("用户请求停止扫描")` 实现可中断的长耗时任务。

## 3. 架构与约定

### 3.1 数据库连接的事务封装
`duplicate_finder._get_db_connection` 和 `visual_similarity._get_db_connection` 均使用 `@contextmanager` 包装 sqlite3 连接：
```python
@contextmanager
def _get_db_connection(self):
    conn = self._get_connection()
    try:
        yield conn
        conn.commit()
    except Exception as e:
        conn.rollback()
        raise e
    finally:
        conn.close()
```
所有写操作都通过此上下文管理器进入，确保异常时回滚并关闭连接。`_get_connection` 设置 `timeout=60`、`busy_timeout=60000`、`PRAGMA journal_mode=WAL` 等参数缓解 SQLite 锁冲突。

### 3.2 可中断扫描
`DuplicateFinder._check_stop` 检查 `self.stop_flag.is_set()`，若为真则 `raise InterruptedError("用户请求停止扫描")`。该异常在并行任务的 `future.result()` 处被重新抛出，并在 GUI 层的 `_run_scan` 中被 `except InterruptedError` 捕获，仅记录日志而不视为失败。

### 3.3 可选依赖的优雅降级
`software_version_detector.py` 顶部：
```python
try:
    import pefile
except ImportError:
    print("Warning: pefile not installed...")
    pefile = None
```
后续逻辑根据 `if not pefile:` 走回退路径（字符串比较版本号、跳过 PE 元数据提取），保证工具在无可选依赖时仍可运行。

### 3.4 单文件 I/O 的容错
- `duplicate_finder._scan_single_directory` 中对每个文件 `os.stat`/读取包裹 `try/except (OSError, PermissionError)`，仅 `print` 警告后 continue，不中断整个扫描。
- `_compute_partial_hashes` / `_compute_full_hashes` 内部函数捕获 `Exception` 后 `print(f"错误: 无法读取文件 {file_path}: {e}")` 并返回 `None`，由外层聚合过滤掉失败项。
- `_log` 方法捕获 `UnicodeEncodeError`，回退到 GBK 编码输出，避免 Windows 控制台编码问题导致崩溃。

### 3.5 GUI 层错误呈现
GUI 中所有耗时操作都在 `threading.Thread(target=..., daemon=True)` 中运行，`_run_scan` 结构统一为：
```python
def _run_scan(self):
    try:
        # 执行业务逻辑
    except InterruptedError:
        self._log("扫描已停止", "INFO")
    except Exception as e:
        self._log(f"扫描失败: {e}", "ERROR")
        messagebox.showerror("错误", f"扫描过程中发生错误:\n{e}")
    finally:
        # 恢复按钮状态、进度条
```
用户可见的错误全部通过 `messagebox.showerror` / `messagebox.showwarning` / `messagebox.showinfo` 弹出，而非抛到 Tk 事件循环。

### 3.6 无全局异常类/错误码
仓库未定义任何 `class XxxError(Exception)`，也未集中定义错误码枚举。错误传播方式完全依赖 Python 内置异常（`InterruptedError`、`IOError`、`OSError`、`PermissionError`、`ValueError`、`TypeError` 等）和通用 `Exception`。

## 4. 约定与约束

| 约定 | 说明 | 证据 |
|---|---|---|
| 长耗时任务必须支持中断 | 通过 `stop_flag` + `InterruptedError` 实现 | `duplicate_finder._check_stop`、GUI 各标签页 `_stop_scan` |
| 数据库写入必须经上下文管理器 | 所有写操作使用 `_get_db_connection` 上下文，异常时自动 rollback | `duplicate_finder._get_db_connection`、`visual_similarity._get_db_connection` |
| 单个文件 I/O 失败不应中断批量扫描 | 捕获 `OSError/PermissionError` 后 `continue` | `_scan_single_directory` 中逐文件 try/except |
| 可选依赖以 `try/except ImportError` 降级 | `pefile`、`packaging` 缺失时仍可用 | `software_version_detector.py` 顶部导入块 |
| GUI 异常不得冒泡到 Tk 事件循环 | 所有后台线程用 try/except 包裹，错误通过 messagebox 展示 | `exact_match_tab._run_scan` 及同类结构 |
| 日志通过回调上报而非全局 logger | 引擎暴露 `log_callback`，GUI 层注入 `_log` | `DuplicateFinder.__init__` 的 `log_callback` 参数 |
| 多线程进度更新加锁 | 使用 `threading.Lock` (`_progress_lock`) 保护计数器 | `_compute_partial_hashes`、`_compute_full_hashes` 中 `with self._progress_lock` |

## 5. 不足与风险

- 没有统一的业务异常类型，调用方难以区分“用户主动停止”和“真实错误”，目前靠 `InterruptedError` 这一特例区分，但并非所有模块都遵循。
- 大量 `except Exception as e` 仅打印/记录后忽略，可能掩盖潜在 bug（如 `core/video_similarity.py` 多处吞异常）。
- 未使用结构化日志（无级别、无时间戳、无来源定位），调试大规模扫描时定位困难。
- GUI 层缺少全局异常钩子（`sys.excepthook`），如果某个非线程代码路径抛出未捕获异常，Tk 会直接崩溃。
